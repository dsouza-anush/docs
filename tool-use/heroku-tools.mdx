---
title: "Heroku Tools"
description: "Built-in tools that enable AI agents to execute code and query databases on Heroku"
---

Heroku tools let agents execute code, query databases, and run commands in secure, isolated environments. Unlike custom tools that require you to build and host MCP servers, these built-in tools work immediately with the Agents API.

## How tools work

When you include a Heroku tool in an agent request, the agent can decide to call it based on the conversation. Each tool invocation:

1. Spins up an isolated one-off dyno on your target app
2. Executes the operation (code, query, or command)
3. Returns the output to the agent, which incorporates it into its response
4. Shuts down the dyno automatically

This isolation means tool executions can't affect your running web dynos and each invocation starts clean.

## Choosing the right tool

| Task | Tool | When to use |
|------|------|-------------|
| Run SQL queries | `pg_psql` | Analyzing data, generating reports, checking database state |
| Execute Python | `code_exec_python` | Data transformations, calculations, API calls |
| Execute Node.js | `code_exec_node` | JSON processing, async operations |
| Execute Ruby | `code_exec_ruby` | Rails-specific logic, Ruby calculations |
| Execute Go | `code_exec_go` | High-performance computations |
| Run custom scripts | `dyno_run_command` | Existing app commands, rake tasks, migrations |
| Semantic search | `pg_vector_query` | RAG retrieval, finding similar documents |
| Parse documents | `doc_reader` | Summarizing PDFs, extracting text |

## Security model

<Warning>
  **Database tools are read-only by design.** All database tools (`pg_psql`, `pg_vector_query`) only work with [follower databases](https://devcenter.heroku.com/articles/heroku-postgres-follower-databases). Followers replicate your primary database but reject all write operations, preventing agents from modifying production data.
</Warning>

Before using database tools, create a follower:

```bash
# Create a read-only follower of your primary database
heroku addons:create heroku-postgresql:standard-0 --follow DATABASE_URL -a your-app

# Wait for the follower to be ready (replication lag should reach 0)
heroku pg:wait -a your-app

# The follower gets a config var like HEROKU_POSTGRESQL_PURPLE_URL
heroku config -a your-app | grep POSTGRESQL
```

Pass the follower's config var name to the tool via `db_attachment` to ensure queries run against the read-only replica.

## Tool Definitions

### dyno_run_command

Execute custom commands on your Heroku app. This tool allows agents to run pre-specified commands, making existing code available for LLM use.

**Use Cases:**
- Run data processing scripts
- Execute application-specific commands
- Trigger scheduled tasks on-demand
- Run diagnostic or health check commands

**Parameters:**
- `cmd` (required) - The command to execute
- `description` (required) - Description of what the command does
- `parameters` (optional) - Input schema for command parameters

**Example:**

```bash
curl $INFERENCE_URL/v1/agents/heroku \
  -H "Authorization: Bearer $INFERENCE_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "claude-4-sonnet",
    "messages": [
      {"role": "user", "content": "Process the latest data batch"}
    ],
    "tools": [
      {
        "type": "heroku_tool",
        "name": "dyno_run_command",
        "description": "Process batch data with custom script",
        "runtime_params": {
          "target_app_name": "my-app",
          "tool_params": {
            "cmd": "python scripts/process_batch.py"
          }
        }
      }
    ]
  }'
```

**Use Cases:**

- Test Ruby code snippets

**Parameters:**

### pg_psql

Execute SQL queries against Heroku Postgres databases. Works like the [`heroku pg:psql`](https://devcenter.heroku.com/articles/heroku-postgresql#pg-psql) CLI command.

**Use Cases:**
- Query database tables and schemas
- Analyze data with SQL aggregations
- Check database statistics and performance
- Retrieve specific records for analysis

**Parameters:**
- `query` (required) - SQL query to execute
- `db_attachment` (optional) - Database config var name (default: `DATABASE_URL`)

**Example:**

```bash
curl $INFERENCE_URL/v1/agents/heroku \
  -H "Authorization: Bearer $INFERENCE_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "claude-4-sonnet",
    "messages": [
      {"role": "user", "content": "Show me all tables in the database"}
    ],
    "tools": [
      {
        "type": "heroku_tool",
        "name": "pg_psql",
        "runtime_params": {
          "target_app_name": "my-app",
          "tool_params": {
            "db_attachment": "HEROKU_POSTGRESQL_PURPLE_URL"
          }
        }
      }
    ]
  }'
```

**Common Queries:**

List all tables:
```sql
SELECT tablename FROM pg_tables WHERE schemaname='public';
```

Get table row counts:
```sql
SELECT schemaname, tablename, n_live_tup AS row_count
FROM pg_stat_user_tables
ORDER BY n_live_tup DESC;
```

Describe a table:
```sql
SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_name='users';
```

### pg_vector_query

Perform vector similarity searches using pgvector on Heroku Postgres databases.

**Use Cases:**
- Semantic search over embedded documents
- Find similar records by vector similarity
- Retrieval-augmented generation (RAG)
- Recommendation systems

**Parameters:**
- `query_vector` (required) - Vector to search for (array of floats)
- `table_name` (required) - Table containing vector column
- `vector_column` (required) - Name of the vector column
- `limit` (optional) - Number of results to return (default: 10)
- `db_attachment` (optional) - Database config var name (default: `DATABASE_URL`)

**Example:**

```bash
curl $INFERENCE_URL/v1/agents/heroku \
  -H "Authorization: Bearer $INFERENCE_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "claude-4-sonnet",
    "messages": [
      {"role": "user", "content": "Find similar documents to my query about machine learning"}
    ],
    "tools": [
      {
        "type": "heroku_tool",
        "name": "pg_vector_query",
        "runtime_params": {
          "target_app_name": "my-app",
          "tool_params": {
            "db_attachment": "HEROKU_POSTGRESQL_PURPLE_URL",
            "table_name": "documents",
            "vector_column": "embedding"
          }
        }
      }
    ]
  }'
```

## Runtime Configuration

All Heroku tools support these runtime parameters:

### target_app_name
**string** · required

Name of the Heroku app where the tool will execute.

### dyno_size
**string** · optional · default: `"standard-1x"`

Dyno size for tool execution. Options: `standard-1x`, `standard-2x`, `performance-m`, `performance-l`.

### ttl_seconds
**integer** · optional · default: `120`

Maximum execution time in seconds. Range: 1-120 seconds.

### max_calls
**integer** · optional · default: `3`

Maximum number of times this tool can be called during the agent loop.

### tool_params
**object** · optional

Tool-specific configuration parameters. See individual tool documentation for available options.

## Production considerations

### Cost control

Each tool invocation spins up a one-off dyno, which consumes dyno hours. Control costs by:

- **Setting `max_calls` conservatively.** Start with 2-3 and increase only if your use case requires more iterations. An agent that calls `pg_psql` 10 times in one conversation costs more than one that retrieves the right data in 2 calls.
- **Using `ttl_seconds` to cap execution time.** Long-running queries or code that hangs will be terminated after this limit, preventing runaway costs.
- **Choosing the smallest viable `dyno_size`.** Most queries and calculations run fine on `standard-1x`. Reserve `performance-m` or larger for memory-intensive operations like processing large datasets.

```json
{
  "type": "heroku_tool",
  "name": "pg_psql",
  "runtime_params": {
    "target_app_name": "my-app",
    "dyno_size": "standard-1x",
    "ttl_seconds": 30,
    "max_calls": 3
  }
}
```

### Writing effective tool descriptions

The `description` field shapes how the agent uses the tool. Be specific about what it does and when to use it:

```json
// Vague - agent may misuse this tool
{
  "description": "Runs database queries"
}

// Specific - agent understands constraints and purpose
{
  "description": "Query the read-only analytics database to retrieve sales data. Use for reporting questions. Cannot modify data. Results are limited to 1000 rows."
}
```

### Debugging tool failures

When tools fail, check these common causes:

| Symptom | Likely cause | Fix |
|---------|--------------|-----|
| "App not found" error | Wrong `target_app_name` | Verify the app name with `heroku apps` |
| Tool times out | Query or code too slow | Add indexes, optimize the query, or increase `ttl_seconds` |
| "No such database" | Wrong `db_attachment` | List attachments with `heroku addons -a your-app` |
| Empty results | Query returned no rows | Not an error—the agent should handle this case |
| Permission denied | Trying to write to follower | Database tools are read-only by design |

View tool execution logs:

```bash
# Watch for one-off dyno activity
heroku logs --tail -a your-app --dyno run
```

### Testing tools before deployment

Test each tool independently before using it in production agent workflows:

```bash
# Test that a SQL query works
heroku pg:psql HEROKU_POSTGRESQL_PURPLE_URL -a your-app -c "SELECT COUNT(*) FROM users;"

# Test that a Python script runs
heroku run python -c "print('Hello from Python')" -a your-app
```

Once you've verified the underlying operations work, test the full tool configuration with a minimal agent request before deploying to users.
